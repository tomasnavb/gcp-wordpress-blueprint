## Priority 2 — Stateless WordPress (backlog task 11)

WordPress stores uploaded media in `wp-content/uploads` on the disk of the instance that handled the upload. Behind the MIG that breaks: a file uploaded to one instance does not exist on the others, so it loads or returns 404 depending on where the load balancer sends the request, and it is lost when the instance is replaced. Plugins and themes installed from the admin panel have the same problem.

Options considered:

| Option | How | For | Against |
|---|---|---|---|
| A. Plugin (WP-Stateless, WP Offload Media) | WordPress uploads media to a bucket and serves it from there | Common in the WordPress world | Credentials live in the application; many plugins expect a service account JSON key, which this project avoids |
| B. Cloud Storage FUSE (`gcsfuse`) | A bucket mounted at `wp-content/uploads` on every instance | No plugin, no keys: uses the instance service account, scoped to that bucket. Low cost | Not a real disk: slower, with limitations. Enough for files written once and read many times |
| C. Filestore (managed NFS) | A shared network disk mounted on every instance | Behaves like a normal disk | Large minimum size, in the hundreds of dollars a month |

**Decision: option B**, pending the research in task 19.

## Priority 3 — Secrets out of the Terraform state

Added on 2026-10-09. The next step of work, after the review of the stateless WordPress branch.

**Problem.** The database password is stored in plain text in the Terraform state, and in every saved plan:

- `random_password.db_password` keeps the generated value in its `result` attribute.
- `google_sql_user.wordpress_app_user` keeps it in `password`.
- `google_secret_manager_secret_version.wordpress_secrets["wordpress-db-password"]` keeps it in `secret_data`.

The state bucket and the plan artifacts in it (`plans/<BUILD_ID>/tfplan`) can be read by anyone with access to that bucket, so the secret is effectively stored twice outside Secret Manager. The state bucket is versioned, so old versions of the state keep it as well.

**Approach.** Ephemeral resources (Terraform 1.10) and write-only arguments (Terraform 1.11): values that Terraform uses during the run but never writes to the state or the plan.

- Generate the password with the ephemeral `random_password` instead of the managed resource.
- Write it with write-only arguments: `secret_data_wo` on the secret version and `password_wo` on the SQL user, each with its `*_wo_version` counter. A write-only value is only sent when its version changes, so the same password reaches both in one apply, and later applies, which generate a new ephemeral value, do not overwrite it. Rotating the password is bumping the version.
- Alternative to evaluate: write the password to Secret Manager once and read it back with an ephemeral data source for the SQL user, so Secret Manager is the only source of the value.

**18 — First deploy through the triggers.** The README deploys the first time with `gcloud builds submit`, which uploads the local clone. That came from the original pipeline: the only plan trigger ran on pull requests, and the apply could only use a plan saved by that trigger. A first deploy has no pull request, especially on a fork, so the plan, and therefore the apply, had to be run by hand from the clone.

That is no longer true. `terraform-plan-main` can be run by hand without a pull request and saves its plan, and `terraform-apply` uses it. The first deploy can now go through the triggers, from `main`, like every later deploy:

1. Image: run `packer-build` overriding its substitutions, because the management VPC and the IAP firewall rule it normally uses do not exist yet:

   ```bash
   gcloud builds triggers run packer-build --project=$PROJECT_ID --branch=main \
     --substitutions=_NETWORK=default,_SUBNETWORK=default,_USE_IAP=false
   ```

2. Plan: `gcloud builds triggers run terraform-plan-main --project=$PROJECT_ID --branch=main`.
3. Apply: `gcloud beta builds triggers run terraform-apply` with the `_PLAN_BUILD_ID` of that plan, then approve it in the console.

The clone is still needed, only to run `configs/setup.sh`. `gcloud builds submit` stays documented as the way to test an unmerged branch, which is how the verification deploy of 2026-10-07 was run.

Not verified: whether `gcloud builds triggers run` accepts overriding the substitutions of the `packer-build` trigger as shown.

**24 — Statics bucket with uploads and plugins.** Added on 2026-10-11, as an upgrade to the stateless WordPress work of tasks 20 and 21.

Idea: WordPress finds plugins by scanning `wp-content/plugins`, and the database only stores which ones are active, as paths relative to that folder (the `active_plugins` option). So plugins can be managed as files in a shared folder, like uploads. The uploads bucket would become a statics bucket with a folder per kind of content, each mounted at its place:

| Folder in the bucket | Mounted at |
|---|---|
| `uploads/` | `wp-content/uploads` |
| `plugins/` | `wp-content/plugins` |

Cloud Storage FUSE can mount a single folder of a bucket with `--only-dir`, so it would be two mounts of the same bucket.

To weigh before doing it:

- **It reverses a decision of task 21.** Today plugins come with the image and `DISALLOW_FILE_MODS` blocks the admin panel from changing them. With plugins in the bucket they stop being part of the image: decide whether the panel may install them again, or whether they are only copied into the bucket from outside.
- **Security.** Plugins are code that the instances execute. Whoever can write to that folder, or takes over a WordPress admin account if the panel can install plugins, runs code on every instance. Uploads do not have that risk. The plugins folder would need tighter write access than the uploads folder; a read-only mount on the instances, with plugins copied in by the pipeline, keeps the immutability of today.
- **Performance.** Cloud Storage FUSE is slow with many small files, and a plugin is exactly that, read on every request. PHP OPcache softens it, but it still checks the files for changes unless told not to. Measure before adopting it.
- **Rename.** Done on 2026-10-11, before any deploy: the bucket is `wordpress-statics-<project_id>`, its name is a fixed local instead of a variable, and uploads already live in its `uploads/` folder, mounted with `--only-dir uploads`. Adding a `plugins/` folder later does not move any existing data.
- Themes have the same nature as plugins (`wp-content/themes`); decide them together.
