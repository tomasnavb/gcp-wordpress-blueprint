## 1. Admin area behind IAP (R30)

### Why IAP

E4 happened because a fresh WordPress was reachable before it was installed: the installer has no authentication, and whoever completes it first owns the site. Options considered:

| Option | Outcome |
|---|---|
| Install WordPress from the startup script with WP-CLI | **Dropped.** With two instances it needs a lock so that only one installs. The admin credentials have to pass through Secret Manager and stay out of the startup logs. And it only closes the installer: the login stays open afterwards |
| Allow the admin area only from the operator's IP | **Dropped.** The operator's IP changes, and every change becomes a Terraform change |
| IAP on the admin area and the login | **Chosen.** Closed from the first apply, the installer is completed once by the operator through IAP, and the login keeps a Google identity check in front of WordPress's own |

### Design

The module `global_external_lb` gets an optional second backend service on the same MIG, `mig_iap`, with IAP enabled. Nothing is created when `iap_protected_paths` is empty, so the module still works without IAP.

| Input | Value in the root module (`locals.tf`, `compute.tf`) |
|---|---|
| `iap_protected_paths` | `/wp-admin`, `/wp-admin/*`, `/wp-login.php` |
| `iap_public_paths` | `/wp-admin/admin-ajax.php`, which the public site calls from the browser |
| `iap_members` | `user:${var.iap_user_email}`, the same operator account that has SSH through IAP. To be replaced by a Google group (T46) |

Members get `roles/iap.httpsResourceAccessor` on that backend service only, not on the project.

**Path rules.** The URL map matches by specificity, not by order: an exact path first, then the longest `/*` prefix, then the default of the path matcher. So `/wp-admin/admin-ajax.php`, an exact path, wins over `/wp-admin/*`. `/wp-admin/*` does not match `/wp-admin` without the slash, which is why it is listed as an exact path too.

**Organization prerequisite.** IAP uses the Google-managed OAuth client, which only admits accounts of the project's organization. The operator account must belong to it. Documented in the README and in `configs/setup.sh`.

### Cloud Armor runs before IAP

On a global external Application Load Balancer, Cloud Armor evaluates a request before IAP, and a rule cannot see which backend service the request is routed to. Two consequences:

1. **Two security policies,** one per backend service. Each rule is defined once, in a local, and each policy takes the ones it needs:

   | Priority | Rule | Public policy | IAP policy |
   |---|---|---|---|
   | 50 | Block unknown hosts | yes | yes |
   | 100 | Block `xmlrpc.php` | yes | no, never routed there |
   | 150 | Block protected paths outside IAP | only when IAP is enabled | no |
   | 200 | Login rate limit and ban | only when IAP is disabled | yes |
   | 1000+ | Preconfigured WAF rules | yes | yes |

2. **Rule 150 is needed.** The path rules compare the path as it arrives, but Apache and PHP read it more loosely: `/wp-login.php/x` runs `wp-login.php`, and `//wp-admin/` or an encoded character reach the same files. Such a request matches no protected path rule, goes to the public backend, and skips IAP. Rule 150 blocks, on the public backend, any path that contains a protected path after `urlDecodeUni().lower()`, except the exact public paths. Fifteen path variants were checked against the generated RE2 expression before committing.

The login rate limit moves to the IAP policy, because that is where the login is served. It still matters there: a compromised Google account with access could try WordPress passwords.

### Known limits

- **The IAP JWT is not verified by WordPress.** Google recommends it as a backstop for a request that reaches the application without going through IAP. Two things stand in for it here: the firewall only admits the Google front ends on the backend port, so a request cannot reach an instance around the load balancer; and rule 150 blocks a path that would avoid the protected path rules. Rule 150 depends on Cloud Armor decoding and normalizing the path as expected, which the smoke tests check. Verifying the `x-goog-iap-jwt-assertion` header in a mu-plugin was considered and deferred.
- **Access goes through one user account** until T46 replaces it with a group.

## 2. Only the site's domains (R28, R29)

The host rule of the URL map was `hosts = ["*"]`. In E4 the logs showed scanners reaching the installer with the load balancer IP, its reverse DNS name and a third-party domain as `Host`. It now takes `var.domain_names`.

A request with any other host goes to the URL map default. The default cannot deny: a URL map has no such action, only a backend service, a backend bucket or a redirect.

| Default considered | Outcome |
|---|---|
| A redirect to the site | **Dropped.** It hands the site's domain to whoever sent the request |
| An empty bucket | **Dropped.** One more resource reachable from anywhere |
| The public backend service, with a Cloud Armor rule that answers 403 to unknown hosts | **Chosen** |

The rule (priority 50) is `!has(request.headers['host']) || !request.headers['host'].lower().matches(...)`, with the domains joined into an anchored regular expression and an optional port. Header keys in Cloud Armor are lowercase. Health checks do not go through Cloud Armor, so they are not affected. The module validates `domain_names` as lowercase hostnames, so the expression cannot be broken by the input.

`X-Forwarded-Host` was left as it is: WordPress does not read it for its address once `WP_HOME` and `WP_SITEURL` are set.

**Site address (R29).** WordPress builds its links and redirects, the password reset link among them, from `WP_HOME` and `WP_SITEURL`. Without them, it falls back to the request, and the `Host` header is written by the client (PortSwigger, "How to prevent HTTP Host header attacks"). Terraform passes the first domain as the `site-url` metadata key. The startup script checks that it is an `https://` URL with a plain hostname and writes both constants into `wp-config.php` between markers, replacing the block on every boot.

## 3. Pinned downloads (T20)

Every piece of software the image installs is downloaded at an exact version and checked against a SHA256 committed in the repository, before anything is extracted.

- **WordPress 7.1.3.** WordPress publishes only SHA1 and MD5. The SHA1 is checked once, when the version changes, by `packer/scripts/update-checksums.sh`; the build compares against the committed SHA256 in `packer/scripts/checksums.sha256`. The checksum never comes from the same server as the file at build time.
- **Language packs:** core packs for ten locales (`es_ES es_AR de_DE fr_FR it_IT ja nl_NL pl_PL pt_BR ru_RU`), and the packs of Twenty Twenty-Five, the default theme, which has no `es_AR`. About 48 MB on a 10 GB disk.
  - They go in the image because `DISALLOW_FILE_MODS` turns off language installs from the admin panel, and a pack installed on one instance would be lost when the MIG replaces it.
  - Not installed with WP-CLI: `wp language core install` needs the database, and it does not verify checksums. They are downloaded from the same URLs WP-CLI uses, listed by the translations API.
  - The translations API publishes no checksum. WordPress.org rebuilds a pack when its translations change without a new version, so a rebuilt pack fails the build until its SHA256 is reviewed and updated.
  - The installer shows no language chooser with `DISALLOW_FILE_MODS` (`wp_can_install_language_pack()` is false). The site language is chosen after the installation, in Settings > General.
- **`update-checksums.sh`** reads the versions and locales from `install.sh`, so they are written in one place, checks the official SHA1, checks that `THEME_VERSION` is the theme bundled in that release, and rewrites the checksum file. Its diff is reviewed in the PR.
- **Packer plugin `googlecompute` 1.2.7**, an exact version instead of a range: Packer has no lock file, so a range would let two builds of the same commit use different plugin versions.

## 4. Application passwords disabled (R31)

Application passwords authenticate the REST API with Basic authentication, through `/wp-json/`, which is not behind IAP. A stolen admin session could create one and keep access without going through IAP again. The image adds a mu-plugin, `wp-content/mu-plugins/disable-application-passwords.php`, with `add_filter( 'wp_is_application_passwords_available', '__return_false' );`. A mu-plugin cannot be disabled from the admin panel.

## 5. Two instances (R32)

`min_replicas = 2`. With one instance, every replacement (a rollout, auto-healing, a zone outage) is downtime. It also matters for IAP: the operator completes the installer through either instance, and both read the same database.

## 6. Domains passed by the pipeline

`domain_names` was written in `terraform.tfvars`. A fork that deployed without changing it would request a managed certificate for someone else's domain. It now comes from the `_DOMAIN_NAMES` substitution of the plan triggers, like the project ID and the operator email:

- `var.domain_names` is a comma-separated `string`, because a substitution holds a string. `local.domain_names` splits it. A validation rejects anything that is not lowercase hostnames, so the placeholder `your-domain-names` in `terraform-plan.yaml` fails the plan.
- `configs/setup.sh` requires `DOMAIN_NAMES` and stores it in the triggers.
- The triggers and the README commands use `--substitutions="^;^K1=V1;K2=V2"`. gcloud splits the substitutions on commas by default, which would cut `a.com,b.com` in two; a leading `^;^` changes the separator to `;` (`gcloud topic escaping`). The double quotes are required: bash would otherwise end the command at the first `;`.

## 7. Point-in-time recovery (T32)

```hcl
backup_configuration {
  enabled                        = true
  binary_log_enabled             = true
  start_time                     = "02:00"
  transaction_log_retention_days = 7
  backup_retention_settings {
    retained_backups = 8
  }
}
```

- **Binary logs, not `point_in_time_recovery_enabled`.** MySQL replays its binary log, a logical log of changes. PostgreSQL and SQL Server replay their own transaction log (WAL in PostgreSQL). Each engine reads only its own format, so the provider has one field per engine: `point_in_time_recovery_enabled` is valid only for PostgreSQL and SQL Server.
- **7 days of logs,** the maximum for MySQL on Enterprise edition (1 to 7).
- **8 backups.** Google recommends one more backup than days of log retention, and gives this example: 7 days of logs, 8 backups. Log retention must not exceed backup retention.
- **Backup window at 02:00 UTC.** `start_time` is in UTC; the scheduler of the daily export runs at 00:00 in `Europe/Paris` (22:00 or 23:00 UTC). The backup starts three to four hours after the export.
- **The daily export stays.** It does not interact with the binary logs or the automated backups (it runs with `offload`, from a temporary instance). The two cover different failures:

  | Failure | Automated backups and binary logs | Daily export |
  |---|---|---|
  | A bad change at a known time | Restore to the minute before | Restore to the last export |
  | The instance is deleted | Lost with it (`deletion_protection = false`) | Kept in the bucket |
  | Data needed in another project or engine version | Tied to Cloud SQL | A portable `.sql` |

  A point-in-time restore always creates a new instance; it starts from an automated backup, never from an export. Both procedures go in the restore runbook (T33). The export bucket is in the same project, so deleting the project loses both.

## 8. Tests

- **`tests/smoke/edge-security.sh`** runs against the deployed site with `curl` and checks the edge: unknown hosts and `xmlrpc.php` get a 403; the protected paths are sent to IAP, and their variants (`/wp-login.php/x`, `//wp-admin/`, an encoded or uppercase path) get a 403; `admin-ajax.php`, `/health.php` and the uploads are served without IAP. Reaching WordPress is accepted as either `admin-ajax.php` without an action, which answers `400` with body `0`, or, before the installation, a `302` to `https://<domain>/wp-admin/install.php`. The redirect also proves that WordPress takes its address from `WP_HOME`.
