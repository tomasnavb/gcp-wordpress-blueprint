# Devlog — 2026-10-25

Decisions of block 5 of the refactor: the edge layer of the load balancer (tasks R23 to R26 in [../to-do.md](../to-do.md)). Nothing was deployed; everything below is in the code and is checked in the deploy of R22.

What the block adds, in `terraform/modules/global_external_lb`:

- A backend bucket that serves `/wp-content/uploads/*` from the uploads bucket, through Cloud CDN.
- Cloud CDN on the backend service of the instances.
- A Cloud Armor security policy on the backend service.

## 1. Uploads served from a private bucket

**Question.** Can the uploads bucket stay private (public access prevention enforced, like every other bucket) and still be served by the load balancer and Cloud CDN?

**Answer.** Yes. Private Bucket Access has been generally available since 2026-07-03: the load balancer reads the bucket with a Google-managed service account, `service-<PROJECT_NUMBER>@https-lb.iam.gserviceaccount.com`, which needs `roles/storage.objectViewer` on the bucket. No signed URLs, no `allUsers`.

Notes from the documentation:

- The service account only exists once the project has its first backend bucket, so the binding depends on the backend bucket.
- It is read-only: no `POST`, `PUT`, `PATCH` or `DELETE` through the load balancer. WordPress writes the uploads through Cloud Storage FUSE with the instance service account, so this does not affect it.
- The project number comes from `data "google_project"`; it is not written in the code.

**What "private" means here.** The bucket is private, the content is not. Anyone can still get `/wp-content/uploads/...` through the site. What is gained is a single way in: no direct reads from `storage.googleapis.com`, no listing, and every request goes through the load balancer, Cloud CDN and its logs. That is what public WordPress uploads need.

**Uploads are public by design.** WordPress serves `wp-content/uploads/` as static files, without checking who asks: an image in a private post is still readable by URL. Per-user private files (membership or download plugins) need application-level access control, such as signed URLs, and must not go in this bucket. A plugin that protects files inside `uploads` with `.htaccess` is not compatible with the backend bucket, because those requests no longer reach Apache.

## 2. Cache modes

| Backend | Cache mode | Why |
|---|---|---|
| Uploads bucket | `FORCE_CACHE_ALL` | Required to cache a private bucket ("for private bucket access, you must set the `FORCE_CACHE_ALL` cache mode"). Safe: a bucket returns the same object to everyone for a URL, with no per-user responses |
| Instances (WordPress) | `CACHE_ALL_STATIC` | Caches static content types and respects the origin: never caches responses with `Set-Cookie`, `Cache-Control: private` or `no-store`, nor HTML without caching headers. `FORCE_CACHE_ALL` here could serve one logged-in user's page to another |

Why `FORCE_CACHE_ALL` is needed for the private bucket is only partly documented. Cloud Storage always sends a `Cache-Control` header to Cloud CDN, and assigns `public, max-age=3600` to public objects without metadata. The header it sends for non-public objects is not stated in the pages read; it presumably prevents caching, which `FORCE_CACHE_ALL` overrides.

**TTLs.**

- `default_ttl`: how long Cloud CDN keeps a response. With `CACHE_ALL_STATIC` it applies only to responses without a TTL of their own; with `FORCE_CACHE_ALL` it always applies.
- `max_ttl`: the cap in Cloud CDN for `CACHE_ALL_STATIC`. It cannot be set with `FORCE_CACHE_ALL`, so the backend bucket does not set it.
- `client_ttl`: the cap of the `max-age` sent to browsers. It can only lower it.

Values:

| Backend | `default_ttl` | `max_ttl` | `client_ttl` |
|---|---|---|---|
| Uploads bucket | 3600 | — | 3600 |
| Instances | 3600 | 86400 | 3600 |

A new upload gets a new file name (WordPress appends `-1` when the name exists), so it is never served stale. The uploads TTL bounds how long a deleted or overwritten file keeps being served. It was first set to a day and lowered to an hour: the site has little traffic and Cloud Storage is a cheap, fast origin, so a shorter TTL costs little and keeps the worst case at an hour. For an urgent removal, the path is invalidated in Cloud CDN; browsers keep their copy up to `client_ttl`, which is why it is also an hour.

## 3. Cloud Armor

The policy is attached to the backend service of the instances. A cache hit never reaches it. Rules, by priority:

| Priority | Rule | Action |
|---|---|---|
| 100 | `xmlrpc.php` | `deny(403)` |
| 200 | `POST` to `wp-login.php` | `rate_based_ban` |
| 1000–1010 | Preconfigured WAF rules, OWASP Core Rule Set 4.22 | `deny(403)`, in preview |
| 2147483647 | Default | `allow` |

### xmlrpc.php: blocked, not rate limited

`xmlrpc.php` is the XML-RPC API of WordPress (remote publishing, pingbacks), which this site does not use. Its `system.multicall` method tries hundreds of passwords in a single request, so a limit on the number of requests does not stop brute force through it. Pingbacks are also abused for reflection attacks.

### Path expressions

`request.path.matches()` takes an RE2 regular expression and matches anywhere in the path unless anchored. The expressions are `^/+xmlrpc[.]php` and `^/+wp-login[.]php`:

- `^` anchors at the start of the path;
- `/+` also catches repeated slashes, which Apache treats as the same path;
- `[.]` is a literal dot without backslash escaping between HCL and the expression;
- there is no `$`, because PHP also runs `/xmlrpc.php/anything`.

The first version used `'/xmlrpc.php'`, unanchored and with `.` matching any character.

### Login: rate-based ban

Options considered for `wp-login.php`:

| Action | What it does | Outcome |
|---|---|---|
| `throttle` | Requests over the threshold get the exceed action for the rest of the interval. Never bans | Weak against sustained brute force: the threshold keeps letting attempts through |
| `rate_based_ban` | Throttle, plus a ban of `ban_duration_sec` for a client over a second, longer `ban_threshold` | **Chosen** |
| `redirect` to reCAPTCHA | Sends the excess request to a reCAPTCHA challenge | Needs reCAPTCHA Enterprise, and a redirected login `POST` loses the form |

Only `POST` counts: loading the login page is not an attempt.

Values, and how they were reached:

| Parameter | Value |
|---|---|
| `rate_limit_threshold` | 5 per 60 s, a `429` over that |
| `ban_threshold` | 50 per 600 s |
| `ban_duration_sec` | 1800 |

The first version had 10 per minute, a ban over 30 in 10 minutes, and a ban of an hour. That was inconsistent: the throttle let up to 100 attempts through in 10 minutes, but the ban fired at 30, so an IP at 4 attempts per minute was never throttled and still got banned. The ban was acting as the real limit, the opposite of what the ban threshold is for. Google describes it as a way to ban "only clients that frequently exceed the request rate", over a longer window.

References used for the new values:

- **Cloud Armor's login example:** a throttle of 20 requests per 300 seconds (about 4 per minute) on `/login`.
- **Google's tuning guidance:** set the threshold 10% to 30% above normal traffic, measured in Cloud Logging, testing in preview first.
- **WordPress guidance:** about 5 `POST` requests per IP per minute to `wp-login.php` as a common starting point. Not a published standard.
- **OWASP:** account lockout after 3 to 5 failed attempts, for 5 to 30 minutes, as a compromise between stopping attacks and locking out real users.

**How the ban threshold was set.** The ban threshold equals what the throttle lets through over the ban window:

```text
ban_threshold_count >= rate_limit_count × (ban_interval_sec ÷ rate_limit_interval_sec)
50                  >= 5 × (600 ÷ 60)
```

A client that stays within the throttle never reaches the ban; only one that keeps pushing past the limit is banned. Below that figure the ban fires before the throttle and becomes the real limit, which was the problem of the first version. Well above it, the ban takes longer to act against a bot.

This is not Google's "10 times" guidance. A Google Cloud blog post on rate limiting suggests "setting a high ban limit, approximately 10 times the rate limit and to keep the ban duration short". It does not say whether that means the count or the rate, nor over which window, and its own example uses a ban threshold of 110 against a rate limit of 100, over the same 60 seconds. The goal there is to protect backends from misconfigured trusted clients without banning them for short bursts, so a ban that almost never fires. A login needs the opposite: stop brute force. Read literally, ten times the rate over the same window would be a ban only above 50 attempts per minute, which protects nothing. Here the count is ten times, but over a window ten times longer, so the rate is the same as the throttle. A person who mistypes the password a few times reaches neither threshold; a bot is banned within a minute or two. The values are starting points: the load balancer logs mark `RATE_LIMIT_THRESHOLD_EXCEED` and `BAN_THRESHOLD_EXCEED`, and the deploy will show whether they need tuning. The documentation does not say whether requests denied by the throttle count toward the ban threshold.

**Known limit.** Any rule keyed on the client IP can be avoided by a distributed attack, or by password spraying from many IPs, as OWASP warns. Users behind a shared IP (an office, carrier NAT) share the limit. For a site with a single administrator, the stronger measure is to restrict `wp-login.php` and `/wp-admin` to known IPs or put them behind IAP, plus two-factor authentication in the image. Not part of this block.

### Preconfigured WAF rules

- **Version:** CRS 4.22, which Google recommends ("for the most up-to-date protection against modern threats"); generally available since 2026-07-08. The first version used the 3.3 rule sets, taken from an example. 4.22 reclassifies the `nodejs` set as `generic`, adds signatures in protocol attack, PHP and RCE, and its method enforcement allows only `GET`, `HEAD`, `POST` and `OPTIONS`.
- **Rule sets:** `sqli`, `xss`, `lfi`, `rfi`, `rce`, `php`, `scannerdetection`, `protocolattack`, `methodenforcement`, `sessionfixation` and `generic`, all `-v422-stable`. `java` is left out: it is not part of this stack.
- **Sensitivity 1:** each signature has a level from 1 to 4; lower levels are higher-confidence signatures, less likely to produce false positives. The default is 4, which evaluates every signature. Google's best practice: "start with sensitivity level 1 in preview mode to understand how rules affect your application."
- **Preview mode** (`waf_preview = true`): the rules only log what they would block. The WordPress admin area sends HTML and scripts that can look like attacks, and the REST API defines `PUT` and `DELETE` routes (the block editor normally sends them as `POST` with `X-HTTP-Method-Override`). Matches are reviewed in the logs, then `waf_preview` is set to `false`. The `xmlrpc.php` block and the login limit are enforced from the start.

### Match syntax

A rule matches either with the basic form, `versioned_expr = "SRC_IPS_V1"` with `config { src_ip_ranges }`, or with a CEL expression in `expr`. `config` can only be set with `versioned_expr`. The default rule uses the basic form with `["*"]`; the others need `expr` to read the path and the method or to evaluate WAF rules. An expression that does not mention the IP applies to every client; filtering by IP inside an expression is done with `inIpRange(origin.ip, '...')`.

## 4. Left out

- **Edge security policy on the backend bucket.** It is the only kind of Cloud Armor policy a backend bucket accepts, and it is evaluated before the Cloud CDN cache, so today requests for uploads pass no Cloud Armor rule. Edge policies filter on a subset of attributes (`origin.ip`, `origin.asn`, `origin.region_code`, headers, method, path, query, scheme) and support throttle and rate-based ban; whether they evaluate preconfigured WAF rules is not confirmed in the page read. Left out because the bucket only serves static files that are public by design, with no application behind them to exploit. The realistic risk is mass downloading or hotlinking, which costs egress; if traffic or cost calls for it, the useful rule is a rate limit per IP on `/wp-content/uploads/*` (to-do T44). Source: [Security policy overview (Cloud Armor)](https://docs.cloud.google.com/armor/docs/security-policy-overview).
- **Cost of Cloud Armor and Cloud CDN.** Not checked yet.
