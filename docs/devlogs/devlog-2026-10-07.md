## Deploy errors (2026-10-06)

### D1 — Plan fails: Service Usage and Resource Manager APIs not enabled

**Symptom.** `terraform plan` failed in Cloud Build until `serviceusage.googleapis.com` and `cloudresourcemanager.googleapis.com` were enabled by hand.

**Cause.** Terraform needs Service Usage to enable any other API and Resource Manager to manage project IAM bindings, so it cannot enable these two itself. `configs/setup.sh` only enables `compute.googleapis.com`.

**Fix.** `configs/setup.sh` now enables `serviceusage`, `cloudresourcemanager`, `iam`, `cloudbuild` and `compute` before anything else, and grants `roles/serviceusage.serviceUsageAdmin` to the pipeline SA so Terraform can enable the APIs in `terraform/APIs.tf`. That role was not granted before; the earlier deploys probably worked only because the APIs were already enabled in the project.

**To verify.** Run `setup.sh` and the plan pipeline on a project where those APIs were never enabled by hand.

### D2 — Function build fails reading the source zip and writing logs

**Symptom.** The Cloud Function deploy failed with permission errors until the Compute Engine default service account was given `roles/logging.logWriter` and `roles/storage.objectViewer`.

**Cause.** Deploying a Cloud Function v2 starts a separate Cloud Build that builds the container. That build does not run as the pipeline SA (`terraform-cloud-build`) or as the function's runtime SA. By default it runs as the Compute Engine default SA, which had none of the permissions it needed.

**Fix.** New service account `cloudsql-backup-fn-build-sa`, set in `build_config.service_account` of `google_cloudfunctions2_function.db_backup_fn`, with three bindings:

| Role | Scope | Why |
|---|---|---|
| `roles/storage.objectViewer` | Scripts bucket | Read the source zip |
| `roles/artifactregistry.writer` | Project | Push the image and read the build cache (D3) |
| `roles/logging.logWriter` | Project | Write build logs |

The Artifact Registry role is project-level because Cloud Functions creates the `gcf-artifacts` repository on the first deploy, so Terraform cannot bind to it beforehand. The function depends on the three bindings so the first build does not start before they exist.

The pipeline SA needs `iam.serviceAccounts.actAs` on the build SA; it already has `roles/iam.serviceAccountUser` at project level.

The `roles/storage.objectViewer` binding for the function's runtime SA on the scripts bucket (commit `6a46d4b`) was removed: the build reads the zip, not the running function.

**To verify.** Deploy on a project where the Compute Engine default SA has none of the roles added by hand on 2026-10-06 (`logging.logWriter`, `storage.objectViewer`, `cloudbuild.builds.builder`). The function must build, and both scheduler jobs must run successfully without the removed runtime binding.

### D3 — Function build fails on the Artifact Registry cache image

Worked around by granting `roles/cloudbuild.builds.builder` to the Compute Engine default SA.

**Cause.** Same as D2: the function's build SA had no access to Artifact Registry.

**Fix.** Covered by task 2 (`roles/artifactregistry.writer` on the build SA).

### D4 — VMs cannot write to Cloud Logging

**Symptom.** `logging.logEntries.create` denied for the VM service accounts.

**Cause.** The management VM SA has no logging role. The production VM SA already has `roles/logging.logWriter` in `terraform/IAM.tf`, so if the error also appeared on a production VM the cause is different (binding propagation, or an instance created before the binding). To be confirmed in the next deploy.

**Fix.** New binding `google_project_iam_member.mgmt_vm_log_writer` gives `roles/logging.logWriter` to the management VM SA. Nothing changed for the production VM SA.

**To verify.** In the next deploy, the startup script output of the management VM must appear in Cloud Logging, and the logs of a production VM must show no `logging.logEntries.create` denial. If a production VM still shows it, open a separate item.

### D5 — No way to allow destructive changes when merging to main

**Symptom.** A legitimate refactor that destroys resources (regional load balancer replaced by a global one) cannot pass the plan pipeline.

**Cause.** `_ALLOW_DESTRUCTIVE_CHANGES=false` is fixed in the pull request trigger. The check also runs before the artifact upload, so when it fails the plan cannot even be read.

**Decision.** Merge first, then apply a plan generated on `main`. What is deployed always comes from `main`; a plan from a pull request branch can never be applied. Same model as HCP Terraform (speculative plan on the pull request, real run after the merge).

**Fix.**

| File | Change |
|---|---|
| `cloudbuild/scripts/check_destructive.py` | Two modes via `CHECK_MODE`. `report` lists destructive changes and exits 0. `enforce` fails unless `ALLOW_DESTRUCTIVE=true`, and always fails on protected resources (Cloud SQL instance, its database, backup bucket). Unset defaults to `enforce`. Also fixed the Cloud Run IAM resource type in the safe list (`google_cloud_run_v2_service_iam_member`). |
| `cloudbuild/terraform-plan.yaml` | Runs the check in `report` mode. New `_SAVE_PLAN` substitution: artifacts are uploaded only when it is `true`. `_ALLOW_DESTRUCTIVE_CHANGES` removed. |
| `cloudbuild/terraform-apply.yaml` | Converts the downloaded plan to JSON and runs the check in `enforce` mode before applying. New `_ALLOW_DESTRUCTIVE` substitution, default `false`. |
| `configs/setup.sh` | `terraform-plan` renamed to `terraform-plan-pr` (`_SAVE_PLAN=false`). New `terraform-plan-main` on push to `main` touching `terraform/**` (`_SAVE_PLAN=true`). |
| `README.md` | CI/CD flow, destructive change rules and destroy procedure rewritten. |

A full teardown no longer goes through the pipeline, because the protected resources block it. It is done locally with `terraform destroy`.

The script was tested locally against sample plan JSON files in both modes. The pipelines and triggers were not run.

**To verify.**

- A pull request runs `terraform-plan-pr` and uploads nothing to the state bucket.
- The merge runs `terraform-plan-main` and uploads the plan.
- `terraform-apply` rejects a plan with destructive changes, and accepts the same plan with `_ALLOW_DESTRUCTIVE=true`. The removal of the runtime SA binding from task 2 is a real case to test with.
- Replace the `gcb_activators.png` screenshot in the README: it shows the old trigger names.

## Review findings (2026-10-07)

Found by reading the code. None was reproduced in a deploy unless stated.

**5 — `iap_user_email` placeholder.** `terraform.tfvars` commits `your-email-address`, which produces an invalid IAM member. Pass it to the pipeline as a substitution instead.

**6 — Packer in the management VPC.** The trigger builds in `wordpress-mgmt-vpc`, where SSH is only allowed from the IAP range, and the template does not set `use_iap`. The first manual build works because it uses the `default` network.

**7 — Load balancer IP output.** The README says the IP is shown after apply, but `outputs.tf` is empty. With a managed certificate the IP is also needed to create the DNS record.

**8 — HTTPS detection.** The load balancer terminates TLS and talks HTTP to the backends. WordPress does not read `X-Forwarded-Proto`, which causes redirect loops in the admin area.

**9 — READMEs.** The main README still describes a regional HTTP load balancer with a proxy-only subnet and lists HTTPS in the roadmap. The `external_lb` module README lists the old regional resources and is UTF-16 encoded.

**10 — Management VM to Cloud SQL.** Three separate problems:

- VPC peering is not transitive, so the management VPC has no route to Cloud SQL's private IP through the production VPC.
- The Auth Proxy is started without `--private-ip`, and the instance has no public IP.
- The management VM SA cannot read the `wordpress-db-instance-connection` secret its startup script fetches.

The management VM also boots from the WordPress golden image and runs Apache for no reason.

**11 — Stateless WordPress.** `wp-content/uploads` and plugins live on each instance's disk: lost on replacement, different across instances. The salts in `wp-config.php` keep the sample placeholder.

**12 — Snapshot retention.** The README states 7-day retention for the 4-hourly snapshots. On-demand Cloud SQL backups do not expire and the function never deletes them. Automated backups with binary logging are already enabled on the instance, which makes these snapshots largely redundant.

**13 — Least privilege.**

- `roles/storage.admin` for the Cloud SQL SA on the backup bucket.
- `roles/cloudsql.editor`, `roles/compute.osAdminLogin` and IAP tunnel access at project level for the management VM SA.
- `cloud-platform` scope on every VM.
- The README says credentials are never stored in files; they are written to `wp-config.php` and to the Terraform state.

**14 — Observability.** No Ops Agent, uptime check or alert policy.

**15 — Static analysis.** The plan pipeline runs `fmt` and `validate` only.

**16 — Cleanup.**

- Commented-out firewall rules and variables in the `networking` module and `networking.tf`.
- Unused variable `lb_dedicated_ip_cidr`.
- The note in `APIs.tf` mentions PostgreSQL, MongoDB and a VPC connector that does not exist; `vpcaccess.googleapis.com` is enabled without being used.
- `check_destructive.py` lists `google_cloud_run_service_iam_member`; the resource in use is `google_cloud_run_v2_service_iam_member`.
- `hashicorp/packer:latest` is not pinned.
- `min_replicas = 1` contradicts the zone fault tolerance claim.
- Stray local branch named `origin`.
